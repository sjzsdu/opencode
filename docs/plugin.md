# OpenCode Plugin 包详解

## 概述

`@opencode-ai/plugin` 是 OpenCode 项目的插件开发框架，为开发者提供构建自定义插件的能力。该框架基于 TypeScript 和 Zod 构建，提供类型安全的工具定义、Shell 命令执行、认证管理和会话交互等核心功能。当前版本为 1.1.45，通过 `@opencode-ai/sdk` 与 OpenCode 系统深度集成，支持开发者扩展系统的功能边界。

插件系统的设计理念是让开发者能够以声明式的方式定义工具和认证流程，同时保持与 OpenCode 核心系统的松耦合。这种架构使得插件可以独立开发和测试，同时无缝集成到主系统中。框架提供了丰富的上下文信息和生命周期钩子，让插件能够访问项目状态、执行 Shell 命令、处理用户认证和管理会话状态。

## 包结构

```
packages/plugin/
├── src/
│   ├── index.ts          # 主入口，定义插件接口和核心类型
│   ├── tool.ts           # 工具定义模块，提供声明式工具创建方式
│   ├── shell.ts          # Shell 执行模块，封装 BunShell 操作
│   └── example.ts        # 示例插件，演示插件开发模式
├── script/
│   └── publish.ts        # 发布脚本，处理 npm 包发布流程
├── package.json          # 包配置和依赖声明
├── tsconfig.json         # TypeScript 编译器配置
└── sst-env.d.ts          # 环境类型定义
```

## 核心架构设计

### 插件模型概述

OpenCode 插件系统采用函数式的设计模式，通过 `Plugin` 类型定义插件的基本结构和生命周期。插件本质上是一个异步函数，接收 `PluginInput上下文对象作为参数，返回包含` 各种钩子函数的对象。这种设计允许插件在运行时动态注册工具、配置认证流程和处理系统事件。

插件系统的核心价值在于其扩展性。开发者可以定义任意数量的自定义工具，每个工具都有独立的参数验证、执行逻辑和上下文访问能力。同时，插件可以声明认证钩子，支持 OAuth 等多种认证方式，让系统能够与外部服务安全集成。这种灵活的架构使得 OpenCode 能够适应各种复杂的开发场景和工作流程。

### 类型导出策略

插件包采用精简的导出策略，主要导出两个入口点：主入口 `./index.ts` 提供完整的插件开发接口，包括插件定义、认证钩子、工具注册等核心类型；工具入口 `./tool` 专门用于工具的定义和执行，提供了声明式的工具创建函数。这种分离设计让开发者可以根据需要选择性导入，保持代码的简洁性。

导出内容的组织遵循功能相关性原则：与插件生命周期相关的类型集中在 index.ts 中导出，与工具定义相关的类型在 tool.ts 中导出。Shell 相关的类型作为内部实现细节，通过 BunShell 类型在 index.ts 中导出供插件使用。这种设计既保护了内部实现，又提供了必要的扩展能力。

## 核心类型系统

### 插件输入上下文

`PluginInput` 类型定义了插件运行时的完整上下文环境，是插件与系统交互的主要接口。该类型包含以下关键组件：客户端实例提供 API 访问能力，服务器 URL 标识当前连接的服务地址，工作目录和项目信息提供文件系统的上下文，Shell 实例提供命令执行能力。这种全面的上下文设计让插件能够执行各种复杂的操作。

上下文对象中的 `client` 是 `@opencode-ai/sdk` 创建的客户端实例，插件可以使用它调用任何 OpenCode API。`directory` 字段提供当前项目的工作目录，`worktree` 字段提供项目的根路径，这两个路径对于解析相对路径和生成稳定的文件引用非常重要。`$` 字段是 BunShell 实例，提供类似 Bash 的命令执行能力，支持管道、重定向等高级操作。

### 工具定义类型

`ToolDefinition` 是插件工具的核心类型，通过 `tool()` 函数创建。每个工具定义包含三个关键属性：`description` 提供工具的人类可读描述，用于 AI 模型理解工具的用途；`args` 使用 Zod Schema 定义参数规范，确保传入的参数符合预期类型；`execute` 是实际的执行逻辑，接收解析后的参数和执行上下文，返回字符串结果。

工具系统的设计遵循声明式编程范式，开发者只需要描述工具的接口和功能，框架自动处理参数验证、类型转换和错误处理。Zod 集成使得参数定义既类型安全又富有表现力，支持字符串、数字、对象、数组等各种类型，以及可选参数、默认值、验证器等高级特性。这种设计大大简化了工具开发的工作量，同时保证了运行时安全性。

### 工具执行上下文

`ToolContext` 类型为工具执行提供丰富的运行时信息，是工具与系统交互的桥梁。上下文包含会话标识和消息标识，用于跟踪工具调用的来源和上下文。工作目录信息帮助工具解析相对路径，避免因工作目录变化导致的路径问题。AbortSignal 允许工具响应取消请求，实现可中断的执行流程。

`metadata()` 方法允许工具向系统传递额外的元数据，这些信息可以用于日志记录、性能监控或向用户展示附加信息。`ask()` 方法是权限系统的核心接口，工具可以通过它请求用户授权特定操作，实现需要用户确认的交互式工作流程。这种设计在保持自动化的同时，确保了关键操作的用户可控性。

### Shell 执行接口

`BunShell` 接口封装了 Bun Shell 的全部功能，为插件提供强大的命令行操作能力。Shell 实例支持模板字符串语法，通过 `$` 符号和模板字符串直接编写命令，如 `$`ls -la``。这种直观的语法使得 Shell 命令的编写和阅读都非常自然，降低了命令行操作的学习曲线。

Shell 接口提供了丰富的配置方法：`env()` 设置环境变量，`cwd()` 设置工作目录，`nothrow()` 和 `throws()` 控制错误行为。这些配置可以链式调用，也可以作为参数传递。返回的 `BunShellPromise` 是对命令执行结果的封装，支持多种方式读取输出：`text()` 获取完整文本，`lines()` 逐行读取，`json()` 解析 JSON 响应。

### 认证钩子系统

`AuthHook` 类型支持插件定义自定义的认证流程，特别适用于需要与外部服务集成的场景。认证钩子包含提供商标识和认证方法定义，支持 OAuth 等标准认证协议。每个认证方法可以声明多个提示步骤，引导用户完成认证流程，如输入 API Key、授权访问范围等。

认证系统的设计考虑到了各种认证场景的差异：环境变量方式适合自动化部署，配置文件方式适合开发者使用，自定义方式支持复杂的认证逻辑。插件可以根据需求组合不同的认证方法，系统会自动处理认证信息的获取、缓存和刷新。这种灵活的认证框架使得 OpenCode 能够安全地集成各种外部服务。

## 功能模块详解

### 工具创建函数

`tool()` 函数是创建自定义工具的主要入口，采用声明式的设计范式。函数接收一个配置对象，包含工具的描述信息、参数规范和执行逻辑。描述信息用于 AI 模型理解工具的用途和适用场景，是工具被发现和正确使用的基础。参数规范使用 Zod Schema 定义，支持复杂的类型验证和转换逻辑。

执行函数接收两个参数：解析后的参数对象和执行上下文。参数对象的类型由 Zod Schema 自动推断，确保 TypeScript 编译时的类型安全。执行上下文提供会话信息、工作目录和系统交互能力，工具可以利用这些信息完成复杂的任务。执行函数返回字符串结果，这个结果会被传递给 AI 模型作为工具调用的响应。

工具定义还支持元数据附加，插件可以为工具添加额外的描述信息，如使用示例、注意事项、返回值格式等。这些元数据帮助 AI 模型更好地理解工具的行为，提高工具选择的准确性。框架会自动处理工具注册和发现，插件返回的工具定义会被系统自动收集并注册到工具列表中。

### Shell 命令执行

BunShell 提供了与 Bash 相似的命令执行能力，但采用更加类型安全和可编程的设计。模板字符串语法是最常用的命令编写方式，支持变量插值和表达式求值。表达式可以是字符串、数字、数组或任何可转换为字符串的值，框架会自动处理转义和拼接，避免常见的 Shell 注入漏洞。

命令执行支持多种输出处理模式：`quiet()` 模式只缓冲输出不打印到控制台，适合需要处理输出但不希望干扰用户的场景；`text()` 模式返回完整输出作为字符串；`lines()` 模式将输出按行分割，支持逐行处理大型输出；`json()` 模式自动解析 JSON 格式的输出，返回解析后的对象。这些模式使得处理命令输出变得简单直观。

Shell 实例支持配置继承，通过 `env()` 和 `cwd()` 设置的环境变量和工作目录会应用到后续的所有命令。这种设计避免了每次命令调用都重复配置的问题，也使得命令的执行环境更加可预测。配置方法返回当前实例，支持链式调用，可以在一行代码中完成环境设置和命令执行。

### 错误处理机制

Shell 命令的错误处理通过 `nothrow()` 和 `throws()` 方法控制。默认情况下，非零退出码会抛出异常，这种行为符合"快速失败"的原则，帮助及时发现问题。`nothrow()` 方法可以关闭这种行为，使得命令即使执行失败也不会中断流程，适合需要处理错误但不希望抛出异常的场景。

`throws()` 方法可以显式设置错误处理策略，参数为布尔值，`true` 表示抛出异常，`false` 表示静默处理。这种显式的设置比默认行为更加清晰，代码阅读者可以明确知道当前命令的错误处理策略。错误信息的获取通过捕获异常或检查输出来实现，插件可以根据需求选择合适的错误处理方式。

工具执行函数同样支持错误处理，执行过程中抛出的异常会被框架捕获并记录，错误信息会被传递给 AI 模型用于错误恢复或向用户报告。工具应该尽可能处理可恢复的错误，只在确实无法继续时才抛出异常。这种设计既保证了系统的稳定性，又给了工具充分的错误处理能力。

### 权限请求系统

`ask()` 方法是权限请求系统的核心接口，插件可以通过它请求用户授权特定操作。方法接收一个包含权限描述的对象，包括权限名称、影响文件模式、总是允许选项和元数据。系统会向用户展示权限请求对话框，用户可以选择允许、拒绝或总是允许该操作。

权限请求的设计考虑到了不同场景的需求：文件模式匹配使用 glob 语法，支持匹配单个文件、目录或文件集合；总是允许选项可以让用户记住选择，避免重复确认；元数据可以传递额外的上下文信息，帮助用户理解为什么需要这个权限。这种设计在保持安全性的同时，尽量减少对用户工作流的干扰。

权限状态会被系统缓存，同一权限的后续请求可以直接使用缓存的决策，或者根据"总是允许"设置自动通过。插件可以通过检查权限结果来决定是否继续执行，或者提示用户进行必要的授权。这种权限系统让插件能够执行需要用户确认的操作，同时确保用户对关键操作有最终控制权。

## 使用模式详解

### 基础插件结构

创建插件的基本模式是定义一个返回钩子对象的异步函数。插件函数接收 `PluginInput` 上下文，可以访问客户端、Shell 实例、路径信息等所有必要资源。返回值是一个包含各种钩子的对象，目前主要支持 `tool` 钩子用于注册自定义工具。这种结构清晰地将插件的初始化和功能定义分离，使得插件的逻辑更加清晰。

插件的入口函数应该尽可能简单，只负责资源的获取和钩子的组装。复杂的逻辑应该放在工具定义中实现，这样有利于代码组织和测试。每个工具应该有明确的职责边界，遵循单一职责原则，只做一件事情并做好。这种设计使得插件更容易维护和扩展，也便于编写单元测试验证功能正确性。

插件可以返回多个工具，形成功能丰富的工具集。工具之间可以相互调用，通过共享上下文传递状态和数据。插件还可以定义认证钩子，为需要外部认证的工具提供认证支持。这种模块化的设计让插件能够适应各种复杂的应用场景，从简单的工具扩展到完整的认证集成都可以实现。

### 工具开发最佳实践

工具开发应该遵循以下原则：首先是清晰的描述，一个好的工具描述应该让 AI 模型能够准确理解工具的用途和适用场景；其次是精确的参数定义，使用 Zod Schema 清晰表达参数的类型和约束；然后是健壮的执行逻辑，能够正确处理各种输入和边界情况；最后是有意义的返回值，能够为 AI 模型提供足够的上下文信息。

参数设计应该尽量简单，只暴露必要的参数，避免过多的可选参数增加复杂度。对于复杂的参数结构，可以使用对象类型，将相关的参数组织在一起。参数验证应该足够严格，拒绝不符合规范的输入，但也要提供清晰的错误信息帮助用户理解问题所在。Zod 的验证器功能非常强大，可以实现各种复杂的验证逻辑。

执行函数的实现应该尽量纯粹，尽量避免副作用，使用返回值传递结果而非修改外部状态。这种纯函数式的设计使得工具更容易测试和推理。工具应该处理可预见的错误情况，提供有意义的错误信息，而不是简单地抛出异常。对于需要长时间执行的操作，应该支持取消机制，使用传入的 AbortSignal 来响应取消请求。

### Shell 命令编写规范

编写 Shell 命令时应该注意安全性，避免直接拼接用户输入到命令中。使用 BunShell 的变量插值机制，框架会自动处理转义，防止 Shell 注入攻击。对于必须包含用户输入的场景，应该使用 `escape()` 方法手动转义输入。命令中的特殊字符（如空格、引号、管道符）会被自动处理，但仍需注意边界情况。

命令的输出处理应该选择合适的方式：对于短输出使用 `text()` 直接获取完整文本；对于长输出或需要逐行处理的场景使用 `lines()` 异步迭代器；对于结构化数据使用 `json()` 自动解析。避免使用 `quiet()` 隐藏所有输出，除非确实不需要输出，因为日志记录对于调试和问题排查非常重要。

环境变量和工作目录的设置应该显式进行，而不是依赖当前的进程状态。使用 `env()` 和 `cwd()` 方法设置，确保命令在确定的环境中执行。这种显式的方式使得插件的行为更加可预测，也便于在不同环境中复制执行。环境变量的清理应该及时进行，使用 `undefined` 值可以删除之前设置的环境变量。

## 认证集成模式

### OAuth 认证流程

OAuth 认证需要插件声明 OAuth 类型的认证方法，并定义认证过程中的提示步骤。每个提示可以要求用户输入文本值，支持占位符和验证器。验证器可以检查输入的格式是否正确，如检查 API Key 的长度、格式等。认证完成后，系统会调用可选的 `loader` 函数处理认证信息，返回认证结果。

OAuth 流程的灵活性体现在支持自定义提示步骤的组合。插件可以根据需求定义任意数量的提示，每个提示收集不同类型的信息。提示可以是文本输入，也可以是后续扩展的其他输入类型。验证器的存在确保了收集到的认证信息符合预期格式，减少因认证信息错误导致的集成问题。

认证信息的存储和刷新由系统自动处理，插件只需要声明认证方法和使用认证结果。系统会缓存认证信息，避免频繁重新认证。对于需要刷新令牌的场景，认证逻辑可以包含刷新机制的处理。这种设计让插件开发者能够专注于业务逻辑，而不必担心认证信息的管理细节。

### 环境变量认证

环境变量认证是最简单的认证方式，适合需要自动化部署或 CI/CD 集成的场景。插件声明环境变量名称，系统在需要时从运行环境中读取对应的值。这种方式不需要用户交互，适合无头环境和脚本化使用。环境变量认证可以与配置文件认证或 API 认证组合使用，提供多种认证方式的灵活性。

环境变量认证的配置应该在插件文档中清晰说明，包括需要的变量名称、预期的值格式、获取方式等。用户需要在运行环境中正确设置这些变量，插件才能正常工作。对于敏感信息，环境变量方式比配置文件更加安全，因为环境变量不会写入磁盘或日志文件。

系统会提供加载环境变量失败的错误信息，帮助用户诊断认证问题。插件可以定义多个环境变量认证方法，每个用于不同的外部服务或 API。这种方式保持了插件的模块化，每个外部依赖都有独立的认证声明，便于维护和更新。

## 构建和发布流程

### 编译配置说明

插件包使用 TypeScript 编译器进行构建，配置文件为标准的 `tsconfig.json`。构建脚本 `tsc` 会编译 src 目录下的所有 TypeScript 文件为 JavaScript，生成的文件包含类型声明（.d.ts）和运行时代码（.js）。生成的代码保存在 dist 目录中，作为 npm 包的发布内容。

编译配置遵循项目的统一规范，使用 `@tsconfig/node22` 作为基础配置。编译选项包括严格类型检查、ES 模块输出、源映射生成等。类型声明文件（.d.ts）会被发布到 npm，供使用者在 IDE 中获得类型提示和编译时检查。这种方式既保证了开发时的类型安全，又不影响运行时性能。

构建过程中会进行类型检查，任何类型错误都会导致构建失败。这种严格的要求确保了发布的包是类型安全的，减少使用者遇到类型相关问题的可能性。开发者应该修复所有类型错误后再发布更新，保持包的质量标准。

### npm 发布流程

发布脚本位于 `script/publish.ts`，实现了完整的 npm 包发布流程。发布前会自动修改 package.json 的 exports 配置，将 TypeScript 源路径转换为打包后的 JavaScript 路径。修改后的配置适合 npm 包的运行环境，不会暴露内部实现细节。发布完成后会自动恢复原始配置，保持源码的一致性。

发布使用 `bun pm pack` 创建安装包，然后通过 `npm publish` 推送到 npm 仓库。发布支持版本标签控制，可以发布到 latest、beta 或其他自定义标签。这种灵活的发布机制支持开发流程的不同阶段，如测试版发布、正式版发布、修复版本发布等。

版本号遵循语义化版本规范（Semantic Versioning），当前版本 1.1.45 表示主版本 1、次版本 1、修订版本 45。版本号的递增遵循以下规则：主版本号递增表示存在不兼容的变更，次版本号递增表示新增功能且向后兼容，修订版本号递增表示问题修复和小改进。开发者应该根据变更的性质正确选择版本号的递增方式。

## 开发环境配置

### 依赖要求

使用插件包需要满足以下环境要求：Bun 运行时 1.0 或更高版本用于运行构建和发布脚本；Node.js 18 或更高版本用于 TypeScript 编译和类型检查；TypeScript 5.0 或更高版本用于类型安全的代码开发。这些依赖项可以通过项目的 catalog 机制统一管理，确保团队成员使用一致的工具版本。

`@opencode-ai/sdk` 作为工作区依赖，版本与主项目保持同步。这种依赖管理方式确保了插件与 SDK 的兼容性，避免因版本不匹配导致的问题。zod 依赖用于参数验证和类型转换，是工具定义的重要组成部分。开发者应该熟悉 Zod 的基本用法，能够定义各种参数类型和验证规则。

### 类型安全实践

充分利用 TypeScript 的类型系统可以获得最佳的开发体验。工具的参数类型由 Zod Schema 自动推断，无需手动声明类型。执行上下文的类型在编译时检查，拒绝不符合规范的使用方式。这种静态类型检查能够在开发时发现大部分问题，减少运行时错误。

IDE 的智能提示功能可以帮助开发者快速了解可用的 API 和类型定义。开发者应该善用类型推断和类型断言，避免使用 `any` 类型导致类型检查失效。对于复杂的类型需求，可以定义类型别名或接口来简化代码。类型安全不仅有助于开发效率，也是代码质量的重要保障。

## 性能优化建议

### 工具执行优化

工具的执行函数应该尽可能高效，避免不必要的计算和资源占用。对于耗时的操作，考虑使用流式处理或分块执行，避免长时间阻塞。AbortSignal 的支持使得工具能够响应取消请求，及时释放资源。对于涉及文件系统的操作，应该使用相对路径和缓存机制，减少重复的 I/O 操作。

Shell 命令的执行同样需要注意性能。复杂的命令组合可以拆分为多个简单命令，利用 Shell 的管道和重定向功能实现高效的数据流。避免在循环中执行 Shell 命令，每次命令调用都有固定开销。对于大量相似操作，考虑使用数组操作和批处理方式减少命令调用次数。

### 资源管理最佳实践

Shell 实例和文件句柄等资源应该及时释放，避免资源泄漏。插件的执行是短生命周期的，资源会在插件函数返回后自动清理。但对于长时间运行的场景，开发者应该显式管理资源。AbortSignal 的捕获应该在资源清理代码中检查，确保资源能够被正确释放。

内存使用方面，避免在工具中缓存大量数据，使用流式处理方式处理大型输入和输出。Zod 解析会在内存中创建中间表示，对于超大输入可能造成内存压力。应该设置合理的输入大小限制，或者使用分块处理方式。性能分析可以帮助识别瓶颈，针对性地进行优化。

## 扩展和定制

### 自定义工具开发

开发自定义工具是插件系统的主要应用场景。工具应该专注于特定的功能领域，遵循单一职责原则。一个好的工具应该有清晰的输入输出定义，合理的错误处理，完善的文档说明。工具可以访问会话上下文、文件系统、Shell 执行等能力，合理利用这些能力可以构建功能强大的工具。

工具可以组合使用，通过相互调用实现复杂的工作流。插件可以注册多个相关工具，形成工具集。工具之间可以共享状态，通过上下文传递数据。这种组合能力使得插件能够适应各种复杂的业务需求，从简单的辅助功能到完整的工作流自动化都可以实现。

### 认证集成扩展

插件可以定义多种认证方式，支持与不同的外部服务集成。OAuth 认证适合需要用户授权的场景，如访问用户数据或调用受限 API。环境变量认证适合自动化部署和 CI/CD 场景。配置文件认证适合开发者本地开发使用。每种认证方式都有其适用场景，插件可以根据需求组合使用。

认证信息的获取和使用应该遵循最小权限原则，只请求必要的权限，不过度获取用户数据。认证失败时应该提供清晰的错误信息，帮助用户诊断问题。认证信息的存储和传输应该注意安全性，避免敏感信息泄露。系统提供了基础的认证信息管理能力，插件应该合理利用这些能力。

`@opencode-ai/plugin` 提供了一个功能强大、类型安全的插件开发框架。框架的设计理念是让开发者能够专注于业务逻辑，而不必担心底层的集成细节。通过声明式的工具定义、强大的 Shell 执行能力、灵活的认证集成，插件可以无缝扩展 OpenCode 的功能边界。TypeScript 和 Zod 的集成确保了类型安全，遵循最佳实践可以获得高质量的插件实现。框架的模块化设计使得插件易于开发、测试和维护，是构建 OpenCode 生态系统的理想基础。
